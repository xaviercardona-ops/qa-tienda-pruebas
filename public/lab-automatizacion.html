Laboratorio: mi primera suite automatizada

Ya escribieron casos de prueba a mano y reportaron bugs en Jira. Hoy los convierten en código: pruebas que se ejecutan solas contra la tienda en vivo, encuentran los bugs en segundos y se repiten mil veces sin cansarse. Trabajan en equipo, con Playwright y TypeScript, sobre la misma tienda de las prácticas anteriores.

Qué van a lograr

  • Convertir un criterio de aceptación en una prueba automatizada con la forma Arrange · Act · Assert (Dado · Cuando · Entonces).
  • Escribir localizadores y aserciones que esperan solos, sin pausas fijas, y pruebas independientes entre sí.
  • Distinguir una prueba roja causada por un bug del producto, por un defecto de la prueba, por inestabilidad o por el entorno.
  • Documentar un bug conocido en el código y conectarlo con su issue en Jira.
  • Reducir duplicación con un Page Object y ejecutar la suite en integración continua (GitHub Actions).
Reglas del laboratorio

La tienda no se modifica: es el sistema bajo prueba. Cada prueba es independiente: no puede depender de que otra haya corrido antes (cada una arranca con un navegador limpio). Un rojo no siempre es un bug: primero se diagnostica, después se reporta.

¿Su curso usa Selenium, Cypress, Java o Python? Los conceptos de hoy son los mismos en todas las herramientas. Aquí usamos Playwright con TypeScript porque espera solo a que la página esté lista y trae buenas herramientas de diagnóstico (reporte, capturas y trace).

Antes de la clase

Háganlo con calma el día anterior: no descarguen un navegador entre 30 compañeros a la vez con el wifi de la sala.

  • Node.js 20 o superior. Comprueben con node -v. Si no lo tienen, instalen la versión LTS desde nodejs.org.
  • Git. Comprueben con git --version.
  • Visual Studio Code (recomendado). Opcional: la extensión Playwright Test for VSCode, que permite ejecutar una prueba con un clic.
  • Una cuenta de GitHub por integrante. Una persona del equipo crea el repositorio y agrega al resto como colaboradores.
  • Su plan de pruebas en Jira a la mano (las tareas "Plan de pruebas · US-xx" y los bugs que reportaron): lo van a consultar y a actualizar.
  • ≈ 600 MB libres. Se descarga un navegador de pruebas.

Mapa de la tienda

La tienda no trae identificadores de prueba, así que se ubica cada elemento por su rol y su texto, como lo haría una persona. Todos estos localizadores están verificados: cópienlos. tarjeta, carrito y linea son variables que ustedes crean con las dos primeras filas.

Dos detalles

Playwright normaliza los espacios al comparar texto, así que '$ 65.000' funciona aunque la tienda use un espacio especial. Y en el formulario de envío page.getByLabel('Nombre completo') no encuentra el campo: pruébenlo y descubran por qué. Es un hallazgo; anótenlo.

Parte 1 · Ver pasar y ver fallar

10 min

Antes de escribir una sola línea propia, aprendan a leer una prueba y a ver cómo se ve un rojo.

  1. Ejecuten el ejemplo resuelto viendo el navegador trabajar: 
    npx playwright test 01-catalogo --headed
  2. Abran tests/01-catalogo.spec.ts y lean la primera prueba con esta tabla al lado:
LíneaQué hace
test('CA1: …', async ({ page }) => {Declara una prueba. page es una pestaña de navegador nueva y limpia solo para esta prueba: sin carrito ni memoria de las demás.

Un hábito para toda la vida

Antes de confiar en una prueba, véanla fallar una vez (cambien el valor esperado). Una prueba que nunca ha estado en rojo puede no estar probando nada.

Respondan en ENTREGA.md, sección 5, o en su cuaderno: (1) ¿Qué le pasa a la pestaña del navegador cuando termina la prueba, y por qué importa? (2) ¿Por qué la prueba no usa una espera fija? (3) ¿Cómo supo la prueba que algo estaba mal?

Los avisos del navegador (alert)

Un alert() bloquea la página hasta que alguien lo atiende. Registren el manejador antes de la acción que lo provoca:

let aviso = '';
page.once('dialog', async (dialogo) => {
  aviso = dialogo.message();
  await dialogo.accept();
});
// …aquí va la acción que dispara el alert()…
expect(aviso).toContain('texto que debe decir');

Opcional: grabar para empezar

Ejecuten npm run codegen: se abre la tienda y un grabador que escribe el código mientras ustedes la usan. Sirve para empezar, no para terminar: lo grabado casi nunca tiene aserciones, usa posiciones frágiles como .nth(2) y no tiene nombre ni historia. Convertirlo en una prueba de verdad es parte del trabajo: agréguenle un nombre, un expect con sentido y un localizador por tarjeta en vez de por posición.

Parte 3 · Cazar bugs con pruebas

30 min

Aquí la automatización muestra su valor: una prueba bien escrita encuentra, en un segundo y todas las veces, lo que a mano cuesta minutos. Pero una prueba roja todavía no es un bug: es una pregunta.

1. Escriban al menos 4 pruebas "cazabugs"

Elijan 4 o más de esta lista (están marcadas como CAZABUGS en los archivos). Escríbanlas afirmando lo que dice el criterio de aceptación, nunca lo que la tienda hace hoy.

PruebaArchivoNivel

US-05 · CA2 — "+" respeta el stock02-carrito2
US-06 · CA2 — "−" no baja de 102-carrito2
US-10 · CA2 — un código inválido no borra el descuento03-descuentos-iva2

US-17 · CA3 — el número de pedido tras recargar05-confirmacion3

2. Una prueba roja: ¿y ahora?

  1. Lean el error. Expected contra Received y las líneas del Call log dicen qué esperaba la prueba y qué encontró.
  2. Reprodúzcanlo a mano en la tienda con los mismos pasos. Si a mano todo está bien, el problema es de la prueba.
  3. Revisen la prueba contra el criterio: ¿afirma exactamente lo que el criterio exige, con datos correctos y un localizador que apunta al elemento correcto?
  4. Repítanla para ver si es estable: npx playwright test -g "US-17" --repeat-each=5. Si el resultado cambia sin tocar nada, es inestable.
  5. Descarten el entorno: ¿falló por la red, un navegador distinto o su máquina?
VeredictoCómo se reconoceQué se hace
Bug del productoSe reproduce a mano; la prueba afirma lo que dice el criterio; falla siempre igual.Reportarlo (o actualizar su bug en Jira) y dejar la prueba como fallo esperado.
Defecto de la pruebaLa tienda hace lo correcto y la prueba esperaba otra cosa (dato viejo, localizador equivocado, criterio mal leído).Corregir la prueba.
Prueba inestableA veces pasa y a veces falla sin que cambie nada; --repeat-each da resultados mezclados.Encontrar la causa (esperas, datos, orden). Mientras tanto, cuarentena con test.fixme.
EntornoFalla por la red, la máquina o el navegador; mejora al reintentar o en otra máquina.Documentarlo y usar el Plan B de Problemas frecuentes.

3. Documenten cada bug del producto

  1. Confirmen el bug a mano y búsquenlo en los issues de su equipo en Jira; si no lo reportaron, repórtenlo.
  2. En la prueba, como primera línea, marquen el fallo como esperado con la clave de Jira: 
    test('CA3: …', async ({ page }) => {
  test.fail(true, 'PRJ-12 · descripción corta del bug');
  // …el resto de la prueba, sin cambios…
});
  3. Vuelvan a ejecutarla. Ahora cuenta como passed (la terminal la marca con ✘ porque falló, pero estaba esperado) y el reporte conserva la anotación y el error como evidencia.
  4. En el issue de Jira agreguen un comentario con el nombre de la prueba que lo detecta y una captura del reporte.
Por qué esto es mejor que dejarla roja o borrarla

Una suite roja que nadie arregla entrena a todos a ignorar el rojo. Una prueba borrada olvida el bug. Con test.fail la suite queda verde, el bug queda documentado y, el día que lo corrijan, la prueba "pasará" de verdad y Playwright avisará con un error (Expected to fail, but passed): ese es el momento de quitar la anotación.

Listo cuando: 4 o más pruebas cazabugs escritas, cada una con su veredicto, y npx playwright test termina sin fallos inesperados.

Parte 4 · Datos y pruebas heredadas

20 min

4a. Pruebas dirigidas por datos (10 min)

Cuando varias pruebas solo cambian el dato, no se copian: se generan desde una tabla. El reporte dice entonces exactamente qué filas fallan.

const PRODUCTOS = ['Esfero azul', 'Resma de papel carta'];

for (const nombre of PRODUCTOS) {
  test(`el producto ${nombre} aparece en el catálogo`, async ({ page }) => {
    await page.goto('/');
    await expect(page.getByRole('heading', { name: nombre, level: 3 })).toBeVisible();
  });
}

Implementen una de estas, con una prueba por cada dato:

  • 03-descuentos-iva.spec.ts · US-09 · CA3: variantes de un código válido.
  • 04-checkout.spec.ts · US-15 · CA1 a CA3: CORREOS_VALIDOS (la lista ya está en el archivo).
  • 04-checkout.spec.ts · US-15 · CA4: CORREOS_MAL_FORMADOS.

Cuando fallen solo algunas filas, marquen como fallo esperado solo esas. Una pista con datos de juguete:

const FILAS = [
  { valor: 'a', bug: '' },
  { valor: 'b', bug: 'PRJ-99' },   // esta fila hoy falla por un bug conocido
];
for (const { valor, bug } of FILAS) {
  test(`caso ${valor}`, async ({ page }) => {
    test.fail(bug !== '', `${bug} · razón`);   // solo es "fallo esperado" si la fila trae un bug
    // …
  });
}

Pregunta para ENTREGA.md: ¿cuántas filas fallaron y qué tienen en común? ¿Es un bug o varios?

4b. Pruebas heredadas: ¿qué falló? (10 min)

Un equipo anterior dejó tres pruebas en tests/heredados.spec.ts, en cuarentena con test.fixme, porque nadie sabía por qué fallaban. Para cada una (H1, H2, H3):

  1. Quítenla de cuarentena (borren su línea test.fixme) y ejecútenla: npx playwright test heredados -g "H1".
  2. Diagnostiquen con el flujo de la Parte 3. Para detectar inestabilidad, repítanla muchas veces: npx playwright test heredados -g "H3" --repeat-each=10.
  3. Dejen la prueba en su estado correcto según el veredicto: corregida, documentada como bug conocido o estabilizada.
  4. Anoten en ENTREGA.md (sección 3) el veredicto y cómo lo comprobaron.
Tentación: arreglarla con una pausa

Si una prueba falla "a veces", la solución rápida es await page.waitForTimeout(300). Pruébenla y midan con --repeat-each=30. Después piensen: ¿cuánto habría que esperar en la máquina de un compañero, en la nube o con una red lenta? ¿Cuánto cuesta sumar 300 ms a cada una de 200 pruebas? Una espera correcta no espera un tiempo: espera una condición. Pista: ¿cuándo está realmente lista la página para recibir un clic?

Regla de oro

El Page Object ofrece acciones (agregar, aplicarCodigo…) y entrega localizadores (cantidad, total…). Las aserciones (expect) se quedan en las pruebas, que son las que cuentan qué se espera.

Sobre los reintentos

En la nube la suite reintenta una vez las pruebas que fallan. Si una pasa al reintentar, el reporte la marca Flaky. Un reintento no arregla una prueba inestable: solo la deja en evidencia.

Problemas frecuentes

Dice que no encuentra npm, npx o node

Falta instalar Node.js (versión LTS, 20 o superior) o hay que cerrar y volver a abrir la terminal después de instalarlo. Comprueben con node -v.

npx playwright install tarda mucho o se corta

Es una descarga grande (varios cientos de MB). Reintenten el mismo comando. Si la red de la sala está saturada, instálenlo antes de la clase o pídanle ayuda al docente.

En Windows PowerShell: "la ejecución de scripts está deshabilitada"

Abran Símbolo del sistema (cmd) en lugar de PowerShell, o ejecuten una vez Set-ExecutionPolicy -Scope CurrentUser RemoteSigned y vuelvan a intentar.

Mis pruebas siguen "skipped"

Cada prueba pendiente empieza con test.fixme(true, 'Pendiente de automatizar'). Mientras esa línea exista, la prueba se salta. Impleméntenla y bórrenla.

Todo falla con errores de red, tiempos agotados o de conexión (Plan B)

Si la tienda en línea no responde bien (por ejemplo, porque toda la sala la usa a la vez), corran una copia de la tienda en su computador y apunten las pruebas a ella.

En una terminal, fuera de su repositorio de pruebas:

git clone https://github.com/xaviercardona-ops/qa-tienda-pruebas.git
cd qa-tienda-pruebas
npm ci
npm run dev

Dejen esa terminal abierta. La tienda queda en http://localhost:3000 (si ese puerto está ocupado, la terminal muestra cuál eligió: usen ese). En otra terminal, dentro de su repositorio de pruebas:

# macOS / Linux
BASE_URL=http://localhost:3000 npx playwright test

# Windows PowerShell
$env:BASE_URL="http://localhost:3000"; npx playwright test

# Windows cmd (las comillas evitan que se cuele un espacio al final del valor)
set "BASE_URL=http://localhost:3000" && npx playwright test
npm run report no abre o dice que el puerto está ocupado

Mi prueba pasa en mi computador pero falla en GitHub Actions

Vocabulario

Localizador
La descripción de cómo encontrar un elemento de la página (por su rol, su texto…). Se prefiere lo que ve el usuario sobre la estructura interna del HTML.
Aserción
La comprobación del resultado esperado. En Playwright, las de expect(locator) reintentan hasta que se cumplen o se acaba el tiempo.
Prueba de humo
La prueba mínima que dice si el sistema está vivo y el entorno funciona.
Oráculo
La fuente que dice qué resultado es el correcto. Debe ser independiente de la aplicación: el requisito, no lo que la app muestra.
Dirigida por datos
Una misma prueba que se ejecuta con muchas filas de datos, una prueba por fila.
Inestable (flaky)
Una prueba que a veces pasa y a veces falla sin que nada haya cambiado.
Cuarentena
Apartar una prueba (test.fixme) mientras se investiga, para que no frene a los demás.
Fallo esperado
Una prueba que se sabe que falla por un bug conocido (test.fail). Avisa cuando el bug se corrija.
Page Object
Una clase que concentra los localizadores y acciones de una pantalla, para que las pruebas cuenten la historia y no el HTML.
CI
Integración continua: ejecutar la suite automáticamente en una máquina limpia cada vez que alguien sube cambios.

Verificación y validación · Tema 3.1

Una distinción importante

Verificar no es lo mismo que probar

Verificar · checking

Confirmar lo que ya sabemos

Se conoce el resultado correcto y se comprueba una y otra vez. Se automatiza muy bien.

Ejemplo: ¿DESC10 descuenta el 10 %?

Probar · testing

Explorar lo que no sabemos

Sospechar, hacer preguntas nuevas, aprender del sistema. Necesita a una persona.

Ejemplo: ¿qué pasa si pego un código con emojis?

Bach y Bolton · «Testing and Checking Refined» (2013)

La balanza

Beneficios y riesgos

Beneficios

  • Regresión rápida y repetible
  • Retroalimentación en minutos
  • La misma comprobación, sin cansancio
  • Muchas combinaciones de datos
  • Más tiempo para explorar

Riesgos

  • Inversión inicial y mantenimiento
  • Falsa sensación de seguridad
  • Pruebas inestables: nadie les cree
  • Automatizar casos mal diseñados
  • Elegir la herramienta por moda

Del criterio al código

Anatomía de una prueba

Criterio de aceptación

Dado

que abro la tienda

Cuando

la página termina de cargar

Entonces

veo 8 productos en el catálogo

Prueba automatizada

test('CA1: el catálogo muestra 8 productos',

  async ({ page }) => {

    // Arrange + Act: abrir la tienda

    await page.goto('/');

    // Assert: debe haber 8 productos

    await expect(

      page.getByRole('heading', { level: 3 })

    ).toHaveCount(8);

  });

Arrange · Act · Assert es lo mismo que Dado · Cuando · Entonces, ahora ejecutable.

Verificación y validación · Tema 3.1

Encontrar elementos

Localizadores: de más a menos robustos

1 · Rol y nombre accesible

getByRole('button', { name: 'Agregar' })

Lo que ve y oye el usuario. Se rompe solo si eso cambia.

2 · Texto, marcador o etiqueta

getByPlaceholder('Código de descuento')

Se rompe si cambia la redacción o el idioma.

3 · Identificador de prueba

getByTestId('total')

Estable, pero alguien debe agregarlo: la tienda no los tiene.

4 · CSS o XPath

locator('.rounded-lg p.font-semibold')

Se rompe con cualquier cambio de diseño o de estructura.

Reto para el laboratorio

En el checkout, getByLabel no encuentra el campo

Pruébenlo y descubran por qué. Pista: lo que una prueba no puede encontrar por su nombre, un lector de pantalla tampoco.

Testabilidad = accesibilidad

Verificación y validación · Tema 3.1

Sincronización

Esperar por condición, no por tiempo

Pausa fija

await page.waitForTimeout(3000);

Si la página tarda menos, se pierde tiempo. Si tarda más, la prueba falla igual.

Espera por condición

await expect(

  page.getByText('Tu carrito está vacío.')

).toBeVisible();

Sigue en cuanto se cumple, y falla con un mensaje claro si nunca ocurre.

200 × 0,3 s = 60 s

más en cada ejecución, y en una máquina lenta puede no alcanzar.

Playwright ya espera por ti: cada acción aguarda a que el elemento esté visible, estable y habilitado, y cada expect reintenta hasta 5 s.

Verificación y validación · Tema 3.1

Confiabilidad

Pruebas inestables (flaky)

A veces pasa, a veces falla… y no cambió nada.

Causas frecuentes

Esperas mal hechas

Datos compartidos entre pruebas

Orden de ejecución

Red, hora o servicios externos

Qué provocan

Nadie confía en el rojo.

Se ignoran los fallos… hasta que uno es real.

Se repite «a ver si pasa».

Qué hacer

1. Repetirla muchas veces:

--repeat-each=20

2. Buscar la causa.

3. Cuarentena con test.fixme mientras se arregla.

Un reintento no la arregla: la delata.

Verificación y validación · Tema 3.1

Qué se espera

El oráculo: ¿quién dice qué es correcto?

Copiar lo que muestra la app

const iva = await ivaMostrado.innerText();

await expect(ivaMostrado).toHaveText(iva);

Siempre pasa, aunque el cálculo esté mal. No prueba nada.

Calcularlo desde el requisito

const base = 65000 - 6500;

const iva = base * 0.19;

await expect(ivaMostrado)

  .toHaveText(cop(iva));

Falla si la tienda calcula mal. Eso es una prueba.

Oráculo: la fuente de la verdad, independiente de la aplicación. El requisito, no la pantalla.

Una mochila ($ 65.000) con DESC10: base 58.500 → IVA 11.115 → total 69.615

Diagnóstico

Un rojo no siempre es un bug

Bug del producto

Se reconoce

Se reproduce a mano y falla siempre igual.

Se hace

Reportarlo y marcar test.fail con su clave de Jira.

Defecto de la prueba

Se reconoce

A mano, la tienda hace lo correcto.

Se hace

Corregir la prueba: dato viejo, localizador o criterio mal leído.

Prueba inestable

Se reconoce

A veces pasa y a veces falla; la repetición lo delata.

Se hace

Hallar la causa; mientras, cuarentena con test.fixme.

Entorno

Se reconoce

Falla por red, máquina o navegador; mejora en otra.

Se hace

Documentarlo y usar el Plan B (tienda local).

Leer el error → reproducir a mano → revisar la prueba → repetirla → descartar el entorno

Verificación y validación · Tema 3.1

Mantenibilidad

Page Object: el «cómo» en un solo lugar

Antes · en cada prueba

const tarjeta = page.locator('.rounded-lg')

  .filter({ has: page.getByRole('heading',

    { name: 'Esfero azul', level: 3 }) });

await tarjeta.getByRole('spinbutton').fill('2');

await tarjeta.getByRole('button',

  { name: 'Agregar' }).click();

Después · la historia

await tienda.agregar(

  'Esfero azul', 2);

El «cómo» vive en TiendaPage.ts, escrito una sola vez.

Si la tienda cambia su HTML, se corrige en un lugar, no en 50 pruebas.

Regla de oro: el Page Object ofrece acciones; los expect se quedan en las pruebas.
